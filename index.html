Fovea.

Android → USB → OBS

延遲不是玄學，
是可以拆開來量的。

Fovea 把 Android 手機變成 OBS 的攝影機來源，走 USB。 相機的輸出直接就是硬體編碼器的輸入，中間沒有一次複製； 到了電腦端也不排隊，畫面一到就交給 OBS。 下面是這條路徑上每一段的時間——已經量到的用實心標，還沒量的照實說。

訊號鏈

擷取

手機端 · Kotlin

Camera2 的輸出 Surface 直接綁在 MediaCodec 的輸入上，影格從來沒有 進過 Java 記憶體。編碼器開啟低延遲模式、固定位元率、不產生 B-frame。 自動曝光的 fps 範圍被鎖死，所以光線一暗畫面不會偷偷掉到 15fps。

傳輸

USB · adb forward

走 abstract socket，不在手機上開對外的網路埠，也不需要知道 IP。 轉接是接你電腦上既有的 adb server——我們不夾帶第二支 adb.exe， 因為那正是同類工具用一用就斷線的原因。

解碼

電腦端 · OBS plugin

FFmpeg 低延遲解碼，只用 slice 層級的多執行緒——frame 層級雖然更快， 代價是輸出必然落後好幾格。送進 OBS 時關掉非同步緩衝， 畫面一到就顯示，晚到的直接丟掉。

已經量到的

這些是實際跑出來的數字，不是估的。量測方法、原始樣本與環境限制 都寫在專案的量測文件裡；量不到的部分也一併寫著為什麼量不到。

幾個刻意的決定

用軟體解碼，不用 D3D11VA

硬體解碼本身更快，但結果留在顯示卡記憶體裡，而 OBS 的非同步來源 要的是主記憶體的畫面——把 1080p 讀回來的代價通常比直接軟解還高。

佇列只留三格，而且丟舊的

傳輸跟不上時，你要看到的是最新的畫面，不是三格之前的畫面。 排隊就是延遲，所以寧可丟。

不夾帶自己的 adb.exe

adb server 是單例的。夾帶的版本跟你已經在跑的（例如 Android Studio 的） 不同時，兩邊會互相殺掉重啟，表現出來就是「用一用就要重插 USB」。 我們直接講 adb 的協定，當它的另一個 client。

鎖住自動曝光的 fps 範圍

不鎖的話，光線一暗自動曝光就會把更新率掉到 15fps 去換亮度。 使用者感覺到的是「突然變 lag」，其實是曝光在偷你的影格。

裝起來

兩個部分：手機上的 app，和 OBS 的外掛。外掛裝在使用者層級，不需要管理員權限。

# OBS 外掛
obs-plugin\build.bat

# 手機 app
cd android
gradle assembleDebug
adb install -r app\build\outputs\apk\debug\app-debug.apk

接著在 OBS 加入「Fovea」來源，手機上按開始，插上 USB 就會自己接上。 外掛會用你現有的 adb server 建立轉接，不需要手動下指令。
